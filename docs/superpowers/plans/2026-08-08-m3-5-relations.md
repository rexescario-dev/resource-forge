**Slice:** M3.5 only — Relation / `RelationName` + ordered `relations` sequence + Resource validation; projection non-participation; `operations` remains empty-only

**Goal:** Widen `ResourceSchema.relations` from the empty-only placeholder to an immutable ordered sequence of closed name-only Relations with unique `RelationName`s, validate that sequence as part of `validateResource`, keep independent Field/Relation namespaces, and keep `projectResourceMetadata` free of any Relation contribution.

**Architecture:**

```text
candidate relations sequence
          │
          ▼
 validate candidate member shape   ← closed `{ name }` only; extra props → failure (no stripping)
          │
          ▼
 validate names + uniqueness       ← RelationName grammar + duplicates within relations → failure
          │
          ▼
 snapshot exact valid Relations    ← freeze ordered `{ readonly name }` only; never lossy-normalize candidates
          │
          ▼
       Resource.schema
          │
          ▼
    validateResource               ← authoritative Resource gate; fields per RFC-007; operations still empty-only
          │
          ▼
 projectResourceMetadata           ← revalidate Resource; annotation-derived metadata only; relations contribute nothing
```

**Invariant:** No implementation step may transform an invalid candidate into a valid Relation by discarding information before validation.

`RelationName` is a dedicated Resource-local identity domain (not `FieldName`, not `MetadataKey`). `Relation` is closed: `{ name: RelationName }` only. Declaration order is preserved and participates in sequence equality. Field and Relation uniqueness are independent (same name string may coexist). Equality of sequences is order-sensitive (test/internal helper only; public Resource equality remains deferred).

**Tech Stack:** TypeScript strict, Vitest (existing `packages/core` scripts)

Where this plan and an Accepted specification disagree, the specification wins and this plan must be revised.

## Locked decisions (export / shape review — planning aids)

These freeze the M3.5 implementation surface. They MUST NOT invent product semantics beyond RFC-008.

| Decision | Lock |
| --- | --- |
| `RelationName` | Validated string matching `/^[a-z][a-zA-Z0-9]*$/` exactly. The label “camelCase” is descriptive only — not an extra constraint. Exact string equality; no normalization. Dedicated type/domain — **do not** alias to `FieldName`. |
| `Relation` | `{ readonly name: RelationName }` only. Extra properties → relation-member failure (implementation code `invalid_relation_member`). |
| `relations` representation | **Implementation-level:** `ReadonlyArray<Relation>`. Array index **is** semantic order. |
| Empty `relations` | Zero-length array; still produced by `createEmptyResourceSchema` / `createResource`. |
| `fields` | Unchanged RFC-007 / M3.4 contract (`ReadonlyArray<Field>`). |
| `operations` | Remain `EmptySchemaCollection` (`readonly []`); non-empty → `invalid_schema` **without** a relation (or field) cause. |
| `EmptySchemaCollection` | Keep for `operations` only after this slice; **do not** type `relations` as always-empty. |
| Namespaces | Uniqueness within `relations` only. Field `author` + Relation `author` is valid. No cross-collection uniqueness check. |
| Snapshot construction vs validation | **Separated, non-lossy.** Raw candidate validation (closed shape, names, uniqueness) happens **before** any snapshot that materializes `{ name }` only. `snapshotRelations` accepts only already-validated `Relation` members and freezes an ordered sequence; it MUST NOT discard, strip, or normalize unknown properties. `validateResource` is the final Resource validity gate; it MUST NOT silently rebuild or reorder caller-owned sequences as its primary job. |
| Non-empty Resource construction | **No public builder.** Public `createResource(identity)` remains empty schema collections + empty annotations. Tests needing non-empty `relations` use an **internal** fixture seam (not barrel-exported) that validates candidates before snapshotting. Coexistence tests may pass optional candidate fields through the same internal seam (or a colocated internal helper). |
| Internal helpers | `validateRelationName` / `checkRelations` / `snapshotRelations` / `relationsEqual` are **internal or test-only**, not public product APIs. Public validation remains `validateResource`. |
| Validation ownership | Part of `validateResource` via schema. No public `validateRelations` / `validateResourceSchema`. |
| Schema error taxonomy | Relation failures: `invalid_schema` **with** `cause: RelationValidationError` using only `invalid_relation_name` / `duplicate_relation_name` / `invalid_relation_member` (maps RFC-008 prose causes). Field failures retain `FieldValidationError` causes. Non-member schema failures (missing collections, non-empty operations, non-object schema): `invalid_schema` **without** field/relation cause. |
| `ResourceValidationError.invalid_schema.cause` | Widen to `FieldValidationError \| RelationValidationError` (optional). |
| Projection | After revalidation, still `createResourceMetadata(identity, [...annotations])` only. Relations MUST NOT contribute entries. RFC-007 field projection rules remain unchanged. |
| Reserved names | None. |
| Association / types / constraints | Out of scope. |
| Equality helper | **Test/internal only** `relationsEqual` (order-sensitive). MUST NOT be a public product API. |
| Compose / registry | SHALL NOT require `composeResourceMetadata`; SHALL NOT register. |

### Relation validation error shape (planning aid)

```ts
type RelationValidationError =
  | {
      readonly code: 'invalid_relation_name';
      readonly index: number;
      readonly name: string;
    }
  | {
      readonly code: 'duplicate_relation_name';
      readonly index: number;
      readonly name: string;
    }
  | {
      readonly code: 'invalid_relation_member';
      readonly index: number;
    };

type ResourceValidationError =
  | {
      readonly code: 'invalid_identity';
      readonly cause: IdentityValidationError;
    }
  | {
      readonly code: 'invalid_schema';
      readonly cause?: FieldValidationError | RelationValidationError;
    }
  | {
      readonly code: 'invalid_annotations';
      readonly cause: AnnotationValidationError;
    };
```

Do not invent additional relation cause codes for test convenience. Do not put operations emptiness failures under the three relation causes. Do not put field failures under relation causes.

### Construction vs validation (normative for this plan)

| Concern | Owner |
| --- | --- |
| Validate raw relation candidates (shape / names / uniqueness) | Internal fixture / construction seam — **before** snapshot |
| Establish snapshotted ordered `relations` from **already-valid** Relations | Resource construction seams (`createEmptyResourceSchema` / `createResource` for empty; **internal** fixture for non-empty tests) |
| Decide validity of a Resource’s relations | `validateResource` (final gate on the constructed Resource) |
| Project metadata | `projectResourceMetadata` after revalidation — annotations only |

**Internal non-empty relations fixture seam:**

```ts
// internal / test-only — NOT exported from packages/core public API
// Candidates are opaque objects so extra properties remain observable at runtime.
function createResourceWithRelationsForTests(
  identity: ResourceIdentity,
  candidateRelations: readonly object[],
  annotations?: Annotations,
  candidateFields?: readonly object[],
): Result<Resource, ResourceValidationError>
```

`createResourceWithRelationsForTests` validates candidate relation (and optional field) member shape, names, and uniqueness **before** constructing the snapshot; successful construction freezes the ordered `{ readonly name }` members and then passes the resulting Resource through `validateResource`. Default annotations: `emptyAnnotations`. Default fields: empty sequence.

Failure mapping for the fixture MUST use the same `invalid_schema` + `FieldValidationError` / `RelationValidationError` causes as `validateResource` (no silent success after stripping).

Existing `createResourceWithFieldsForTests` remains for field-focused tests; after this slice it MUST construct empty `relations` as `ReadonlyArray<Relation>` (empty array), not as a permanently empty-typed slot that blocks typing.

### Projection behavior (RFC-008 non-participation)

```text
projectResourceMetadata(resource)
  1. validateResource(resource)     // includes field + relation validity rules
  2. on failure → invalid_resource
  3. createResourceMetadata(identity, [...resource.annotations])  // relations ignored
  4. on metadata failure → invalid_metadata (defensive)
  5. success → ResourceMetadata with identity + annotation-derived entries only
```

MUST NOT mutate Resource. MUST NOT invent relation-derived metadata keys/envelopes. Invalid `relations` MUST fail the projection gate (no bypass because relations contribute nothing).

## Constraints (from Accepted RFC-008)

### SHALL

- represent `relations` as an immutable ordered sequence of name-only Relations
- enforce `RelationName` grammar `/^[a-z][a-zA-Z0-9]*$/` as the sole name constraint
- treat `RelationName` as a dedicated domain (not `FieldName`, not `MetadataKey`)
- enforce unique `RelationName`s within the `relations` sequence only
- allow a Field and Relation to share the same name string on one Resource
- treat empty `relations` as valid
- validate `relations` as part of Resource validity via schema
- keep relation errors distinct from metadata, annotation, and field validation
- preserve declaration order in snapshots; order participates in sequence equality
- validate candidate closed shape / names / uniqueness before any lossy materialization of `{ name }`
- keep `operations` empty-only in this slice
- leave projection free of Relation contributions while still revalidating the Resource

### SHALL NOT

- invent target identity, cardinality, direction, local field handles, or association semantics
- reuse `FieldName` or `MetadataKey` as the Relation identity type/domain
- reserve any `RelationName`s
- introduce a unified cross-collection schema namespace rule
- contribute relations to `projectResourceMetadata`
- silently drop, normalize, coerce, strip unknown properties, dedupe, or reorder for semantic equality
- transform an invalid candidate into a valid Relation by discarding unknown properties before validation
- introduce public `validateRelations` / `validateResourceSchema`
- widen `operations` beyond empty
- invent annotation vocabulary, field types, or field→metadata projection
- export a new public Resource builder solely to support relation tests
- export `relationsEqual` / `validateRelationName` as public product APIs in this slice

## TDD / verification strategy

For each task: write failing tests → implement → green → commit.

**Must cover:**

1. Empty `relations` valid (M3.1 / M3.4 regression)
2. Valid ordered non-empty `relations` accepted via internal fixture; order preserved on Resource
3. Invalid `RelationName` (e.g. `Author`, `line-items`, ``) → `invalid_schema` / `invalid_relation_name`
4. Grammar-valid but “odd camelCase” names (e.g. `userID`) **accepted** — regex is sole constraint
5. Duplicate `RelationName` → `invalid_schema` / `duplicate_relation_name`
6. Extra property on member (e.g. `{ name: 'author', target: 'User' }`) → `invalid_schema` / `invalid_relation_member` via fixture **and** via `validateResource` — never accepted as `{ name: 'author' }` after silent strip
7. Independent namespaces: Field `{ name: 'author' }` + Relation `{ name: 'author' }` → valid Resource
8. Snapshot-by-value / freeze: mutating caller-owned candidate array or member objects MUST NOT change `resource.schema.relations` (only after a **successful** validate-then-snapshot construction)
9. Order-sensitive equality (internal/test): `[author, lineItems] ≠ [lineItems, author]`
10. Non-empty `operations` still → `invalid_schema` (no relation cause required)
11. Projection: Resource with non-empty `relations` + empty annotations → identity + **no** metadata entries from relations
12. Projection: non-empty `relations` + non-empty annotations → annotation entries only (RFC-006 regression)
13. Projection: invalid relations → `invalid_resource` (validation gate; no bypass)
14. Purity: projection does not mutate Resource / relations order
15. Public surface: `Relation` / `RelationName` / `RelationValidationError` exported as planned; `validateRelations` not exported
16. No association / reserved-name / unified-namespace assertions

**Do not:** invent relation→metadata keys; test relation failures via `validateResource` / `invalid_resource` only.
